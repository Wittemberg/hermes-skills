# Production infrastructure rollouts

Use for introducing an application to an existing production environment when the work crosses resource boundaries (for example domain/DNS, reverse proxy, and Docker Swarm). For an app-only Swarm/Traefik deployment, the narrower `swarm-traefik-app-deploy` skill may also apply; preserve its live-stack conventions.

## Procedure

### Image identity and production verification

- Before deploying a container build, record the source commit and a rollback snapshot of the live service/image. Build and push an immutable tag derived from that exact commit, then resolve and pin the registry digest; do not assume a mutable `main` tag still points to your build because CI or another publisher may have overwritten it.
- Before rollout, verify the image's OCI revision label matches the intended commit. Deploy by digest with `start-first` and an explicit rollback policy, then verify the Swarm task is running that digest, the public health endpoint responds, and a changed static asset or version marker from that build is served over the public route. A green health check alone proves availability, not that the intended release is live.
- If the service still runs an older digest after a successful CI build, inspect registry tag/digest and revision labels before changing application code; repair image publication/selection, then roll out the exact digest and verify again.

1. Read the requested rollout plan, the project's write-zone/update rules, and the deployment target. Separate requested end state from the proposed commands and artifacts; do not assume the plan was verified.
2. Collect a read-only baseline from the exact target contexts: cloud identity and account, hosted zone and exact DNS records, public DNS and origin address, host OS/resources, Swarm manager/nodes/networks/stacks, Traefik arguments and working app labels, relevant service mounts and persisted data. Verify the AWS profile instead of assuming `default` and resolve the hostnames through authoritative DNS.
3. Redact secrets before displaying diagnostic output. Do not dump complete container/service environment variables, credentials, token files, `.env`, or authentication stores; request only non-secret fields or filter secrets before output. **Prove configuration in the running process, not just in its mounted file:** a mounted `.env` may contain a key while `process.env` does not; check presence/length/expected format inside the actual container without printing the value, then verify the provider request from that runtime before claiming integration.
4. Test the proposed architecture against actual app requirements before writing deploy artifacts or claiming a feature is integrated: trace every relevant user entry point (including browser text and voice) through the live route, intent compiler, executor bridge, and rendered/spoken result; prove the compiled contract reaches the real executor and its validated result is what the user receives, rather than stopping at a shadow observer or bypassing delegation through a fast path. For a public privileged agent, secure every public route at the proxy before enabling executor dispatch; verify the proxy challenge and application boundary separately, then validate anonymous denial and an authorized request over the public HTTPS hostname. Keep the auth-only rollout separate from enabling the executor so a perimeter failure cannot expose a half-integrated agent. Verify that the middleware applies to all routes, HTTP redirects to HTTPS, and any upstream credential header is removed when the app does not need it; inspect the deployed Traefik version and a working router before writing labels rather than assuming middleware syntax. Verify: process entry point, external runtimes/CLI auth, writable paths, ports/WebSockets, UI/control of a local desktop, data persistence, licensing, trust boundary, and authentication of every externally reachable route.
5. Keep changes inside the repository's durable user-owned extension area. Back up modified user settings first. Create reproducible artifacts with secrets outside the repository/build context; validate syntax/build independently before touching the live Swarm. Distinguish static review, syntax validation, build, deployment, public reachability, and authenticated end-to-end tests as separate evidence levels.
6. Before publishing a hostname, prove that it resolves to the intended origin and identify the authentication/perimeter control. If the owner explicitly authorizes temporary public exposure without authentication, do not silently treat deployment as blocked or as secure: record the accepted exception, visible risk, any available compensating control, and a concrete withdrawal condition; report it prominently. Without explicit risk acceptance, do not expose the unauthenticated service. Prefer `CREATE` over `UPSERT` for intended-new DNS records, then re-read exact records after propagation; inspect and reconcile conflicts before changing existing records.
7. Apply one bounded change at a time. Verify service task health, app logs, routing, certificate, the actual authentication or explicitly accepted exposure state, and a representative user workflow after each rollout. Keep application data separate from the service lifecycle; do not remove volumes or make a destructive rollback without explicit confirmation.
8. Report evidence and limits accurately: current baseline, files/backups, exact changes made, checks actually run, remaining blockers, security risks, and a concrete next action. Never describe an unbuilt or undeployed template as deployed/ready.

See `references/production-preflight.md` for the read-only evidence checklist and validation order. See `references/agent-app-boundaries.md` when the target is an AI agent, desktop automation app, or editor with elevated in-container privileges.
